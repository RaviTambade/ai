 

🌱 **Building MCP Applications with .NET — From Insurance API to AI Agent**

For years, we built enterprise insurance applications with: **C# + ASP.NET Core + SQL Server** We created APIs for:

→ Customers
→ Policies
→ Premiums
→ Claims
→ Agents
→ Employees

A traditional insurance application waits for a user to tell it: **what operation to perform.** Then Generative AI changed the question. Instead of:  “Which API should I call?” we want the AI to understand: **“What is the customer trying to accomplish, and which business capability should I use?”** This is where **MCP — Model Context Protocol** becomes interesting.

 

# 🤖 What problem does MCP solve?

Imagine our Insurance Management System already has these capabilities:

```text
Insurance APIs

GetCustomer()
GetPolicy()
GetPremium()
GetClaim()
CheckClaimStatus()
GetClaimDocuments()
CalculatePremium()
```

Traditionally, an AI application might need custom integration code for every tool. As the number of tools grows:

```text
AI
 │
 ├── Customer API integration
 ├── Policy API integration
 ├── Claim API integration
 ├── Premium API integration
 ├── Document API integration
 └── Reporting API integration
```

The AI application becomes tightly coupled to the enterprise system. MCP introduces a standardized way for AI applications to discover and interact with tools and resources. Think:  **Standardized access to capabilities and context.**
 

# 🏗️ Let's apply MCP to our Insurance App

Imagine a customer asks: **“What is the status of my claim?”** The AI agent shouldn't need to know every implementation detail of the insurance backend. Instead:

```text
Customer
   ↓
AI Assistant
   ↓
LLM
   ↓
MCP Client
   ↓
MCP Server
   ↓
Insurance Tools
   ↓
Insurance APIs / Database
```

The MCP server can expose capabilities such as:

```text
get_customer
get_policy
get_claim
check_claim_status
get_claim_documents
```

The model can select the appropriate capability based on the user's intent.

 

# 🔄 What happens behind the scenes?

A simplified MCP interaction looks like:

```text
1. Host / Client starts
          ↓
2. MCP connection established
          ↓
3. Handshake
          ↓
4. Capabilities negotiated
          ↓
5. Tools / Resources discovered
          ↓
6. User asks a question
          ↓
7. Model determines required capability
          ↓
8. MCP tool invoked
          ↓
9. Insurance system executes operation
          ↓
10. Result returned to model
          ↓
11. AI generates response
```

The important point is: **The LLM is not directly connected to the database.** There is a controlled boundary between: **AI reasoning** and **enterprise capabilities.**

 

# 🛠️ MCP Server for Insurance

Conceptually:

```text
                MCP Server
                    │
       ┌────────────┼────────────┐
       ↓            ↓            ↓
   Customer       Policy       Claims
     Tool          Tool          Tool
       │            │            │
       └────────────┼────────────┘
                    ↓
             Insurance APIs
                    ↓
                SQL Server
```

For example:

```text
Tool: get_claim_status

Input:
claimId

Output:
claimId
status
submittedDate
lastUpdated
```

The AI doesn't need to know how the underlying database query works. It only needs to understand the **tool contract**. That's an important architectural abstraction.
 

# 🧠 MCP + RAG

Now let's combine what we discussed earlier. Suppose the customer asks:  **“Why was my claim rejected?”** There are two kinds of information involved.

### Transactional information

```text
Customer
Policy
Claim
Claim Status
Rejection Reason
```

This can come through tools/APIs.

### Business knowledge

```text
Claim Guidelines
Policy Documents
Coverage Rules
Exclusions
FAQs
```

This can come through RAG.

Now our architecture becomes:

```text
                         AI Agent
                            │
              ┌─────────────┴─────────────┐
              ↓                           ↓
             RAG                         MCP
              ↓                           ↓
       Business Knowledge           Enterprise Tools
              ↓                           ↓
       Vector Database          Insurance APIs / DB
              │                           │
              └─────────────┬─────────────┘
                            ↓
                         LLM
                            ↓
                     Grounded Answer
```

This is much more powerful than simply connecting an LLM to a database.

 
# 🔐 And here comes the most important part

**Security.**

Imagine the user asks: “Show me all claims.” Should the AI be allowed to retrieve every claim? Absolutely not. MCP doesn't magically solve authorization. Our application still needs:

```text
User
 ↓
Authentication
 ↓
Authorization
 ↓
Tool Access Policy
 ↓
MCP Tool
 ↓
Business API
 ↓
Data
```

For example:

```text
Customer
   ↓
Can access → Own policies
Can access → Own claims

Agent
   ↓
Can access → Assigned customers

Claims Officer
   ↓
Can access → Claims within authorized scope

Admin
   ↓
Broader access
```

**AI should never become a shortcut around existing business security.** That's a core enterprise AI principle.

 

# 🧩 MCP is not RAG

This distinction is important. **RAG answers:** “What knowledge should I retrieve?” **MCP enables standardized interaction with capabilities such as tools and resources.** So:

```text
RAG
 ↓
Knowledge

MCP
 ↓
Tools + Resources + Context
```

They can work together.

They solve different problems.

The agent may need to:


That's no longer just: **Chat with an LLM.** It becomes: **AI + Enterprise Data + Enterprise Tools + Business Rules.**
