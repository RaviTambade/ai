# RAG, LLM, MCP, Vector Database and Indexer in an AI-Enabled Insurance Application

Imagine we are building an **AI-enabled Insurance Management System** using:

* ASP.NET Core Web API
* C#
* SQL Server
* LLM
* RAG
* Vector Database
* Indexer
* MCP

The important question is not:  “Where can I add AI?”

The better question is:  **“Which insurance problems should be solved by traditional software, and which problems can be improved using AI?”**


## 1. Start with the Insurance Application

A traditional insurance application may contain:

```text
Customer
Policy
Premium
Claim
Agent
Employee
Documents
Payments
```

The ASP.NET Core application exposes APIs:

```text
POST   /api/customers
GET    /api/customers/101

POST   /api/policies
GET    /api/policies/5001

POST   /api/claims
GET    /api/claims/9001

GET    /api/premiums/5001
```

SQL Server stores structured business data.

For example:

```text
Customer
--------------------------------
Id       Name        City
101      Rahul       Pune


Policy
--------------------------------
Id       CustomerId  Type
5001     101         Health


Claim
--------------------------------
Id       PolicyId    Amount
9001     5001        75000
```

This is where **ASP.NET + SQL Server** are excellent. But insurance companies also have thousands of documents:

```text
Policy Terms
Claim Guidelines
Underwriting Rules
Product Brochures
IRDAI-related documents
Customer Documents
Internal SOPs
FAQs
Terms & Conditions
```

This is where AI architecture becomes useful.


# 2. What is an LLM?

**LLM = Large Language Model**

Examples include models from OpenAI, Microsoft/Azure, Anthropic, Google and others. An LLM is good at understanding and generating natural language. A customer might ask:  “Why was my health insurance claim rejected?” The LLM can understand the question. But there is a problem.

The LLM does **not automatically know your company's latest policy documents or your customer's claim data**.

Therefore:

```text
LLM alone
    ↓
Good language understanding
    ↓
But limited knowledge of your private insurance data
```

We need to provide the right information to the LLM.

That leads us to **RAG**.


# 3. What is RAG?

**RAG = Retrieval-Augmented Generation**

Simple meaning: **First retrieve relevant information, then ask the LLM to generate an answer using that information.**

For example:

Customer asks:  “Why was my claim rejected?”

The system performs:

```text
Question
   ↓
Retrieve relevant informati
on
   ↓
Policy document
Claim information
Claim rules
Customer information
   ↓
Send relevant context to LLM
   ↓
Generate explanation
```

Instead of asking the LLM:

```text
"Why was this claim rejected?"
```

we give it context:

```text
Customer:
Rahul

Policy:
Health Insurance - Silver Plan


Claim:
Hospitalization - ₹75,000

Claim Status:
Rejected

Policy Rule:
Pre-existing conditions are covered only
after the applicable waiting period.

Claim Information:
Treatment was related to a condition
diagnosed 18 months before policy inception.
```
 
Now the LLM can generate:  “Your claim appears to have been rejected because the treatment relates to a pre-existing condition that falls within the applicable waiting-period restriction.”

This is much more useful.


# 4. What is a Vector Database?

A normal SQL database searches structured data. For example:

```sql
SELECT *
FROM Policies
WHERE PolicyNumber = 'POL1001';
```

But users don't always ask questions using exact database fields. Consider: “Does my policy cover treatment for diabetes?” The words in the question may not exactly match the wording inside the policy document. A **Vector Database** helps with semantic search. Documents are converted into numerical representations called **embeddings**.

Conceptually:

```text
"diabetes treatment coverage"
            ↓
        Embedding
            ↓
[0.21, -0.73, 0.44, ...]
```

Another piece of the policy document:

```text
"Treatment related to diabetic conditions
is covered subject to..."
            ↓
        Embedding
            ↓
[0.19, -0.70, 0.46, ...]
```

The vectors are semantically similar. The vector database can therefore retrieve the relevant policy section.


# 5. What is an Indexer?

This is one of the most important components. Suppose the insurance company has:

```text
1000 PDF documents
500 Word documents
2000 FAQs
10000 policy documents
```

We don't want to send all of them to the LLM every time. The **Indexer** prepares the knowledge for efficient retrieval. Think of the indexer as:  **The librarian who reads, organizes, prepares and indexes the company's knowledge.** Typical indexing pipeline:

```text
Documents
   ↓
Read
   ↓
Extract text
   ↓
Clean text
   ↓
Chunk documents
   ↓
Generate embeddings
   ↓
Store vectors
   ↓
Vector Database
```

For example:

```text
Policy.pdf

       ↓

Text extraction

       ↓

Chunking

       ↓

Chunk 1
"Hospitalization coverage..."

Chunk 2
"Pre-existing disease..."

Chunk 3
"Waiting period..."

       ↓

Embedding Model

       ↓

Vectors

       ↓

Vector Database
```

The indexer usually runs **before the customer asks the question**. Therefore:

```text
                         OFFLINE / BACKGROUND

PDF → Extract → Chunk → Embed → Vector DB
                                      │
                                      │
                                      ↓
                              Ready for search
```

# 7. Where does SQL Server fit?

This is very important. **Do not replace SQL Server with a vector database.** They solve different problems. 

SQL Server:

```text
Customers
Policies
Claims
Premiums
Payments
Agents
Transactions
```

Vector DB:

```text
Policy documents
Claim guidelines
FAQs
SOPs
Terms & Conditions
Knowledge articles
```

Think:

```text
             Insurance Application
                    │
        ┌───────────┴───────────┐
        ↓                       ↓
    SQL Server              Vector DB
        │                       │
Structured Data           Unstructured Knowledge
        │                       │
Customer                  Policy documents
Policy                    Guidelines
Claim                     FAQs
Premium                   SOPs
Payment                   Terms
```

Both can work together.



# 8. What is MCP?

**MCP = Model Context Protocol**

For our insurance application, think of MCP as a standardized way for an AI system to interact with **tools and data sources**. Suppose the customer asks:  “What is the status of my claim?” The answer requires actual application data. The AI should not invent it. Instead, it can use a tool such as:

```text
get_claim_status(claimId)
```

The tool calls the ASP.NET application.

Conceptually:

```text
LLM / AI Agent
      ↓
     MCP
      ↓
Insurance Tools
      ↓
ASP.NET APIs
      ↓
SQL Server
```

For example, available tools might be:

```text
get_customer()
get_policy()
get_claim()
get_claim_status()
get_premium_details()
search_policy()
calculate_premium()
create_claim()
```

MCP provides a standardized interface through which an AI client/agent can discover and use such capabilities.


# 9. RAG vs MCP

These two concepts are often confused.

### RAG

RAG answers:  **“What information do I need to know?”**

Example:

```text
Question:
Is maternity treatment covered?

        ↓

RAG

        ↓

Retrieve:
Maternity coverage section
Waiting-period section
Exclusions section
```

### MCP

MCP helps answer:  **“What action or data should I access?”**

Example:

```text
Question:
What is the status of my claim?

        ↓

AI Agent

        ↓

MCP Tool

        ↓

get_claim_status(9001)

        ↓

ASP.NET

        ↓

SQL Server
```

So:

```text
RAG → Knowledge retrieval

MCP → Tool/data interaction
```

# 11. Complete Insurance Example

Customer says:  **“My claim of ₹75,000 was rejected. Can you explain why and tell me whether I can appeal?”** Now the AI-enabled application can perform multiple steps.

### Step 1 — Understand the question

LLM identifies:

```text
Intent:
Claim explanation + appeal information

Claim:
₹75,000
```

### Step 2 — Get actual claim information

The AI agent uses an MCP tool:

```text
get_claim(9001)
```

ASP.NET retrieves the claim from SQL Server.

```text
Claim ID: 9001
Policy ID: 5001
Amount: ₹75,000
Status: Rejected
Reason Code: PRE_EXISTING
```

### Step 3 — Retrieve policy knowledge

RAG searches the Vector Database.

It finds:

```text
Pre-existing disease clause
Waiting-period clause
Claim rejection rules
Appeal procedure
```

### Step 4 — LLM combines the information

The LLM receives:

```text
CLAIM DATA
+
POLICY DOCUMENTS
+
CLAIM GUIDELINES
+
APPEAL PROCEDURE
```

### Step 5 — Generate response

The customer receives a natural-language explanation:

```text
Your ₹75,000 claim was rejected because the
treatment was classified under a pre-existing
condition subject to the policy's waiting period.

According to the applicable policy terms, this
condition was not eligible for coverage at the
time of treatment.

You may appeal the decision by submitting the
required medical records and supporting documents.
```

The important point is: **The LLM did not decide the claim by itself.** The application retrieved actual data and policy knowledge and then used AI to explain it.


# 12. Responsibilities of Each Component

| Component    | Responsibility                           |
| ------------ | ---------------------------------------- |
| ASP.NET Core | Application/API/business services        |
| SQL Server   | Structured insurance data                |
| LLM          | Understand and generate natural language |
| RAG          | Retrieve relevant knowledge              |
| Vector DB    | Semantic storage/search                  |
| Indexer      | Prepare documents for retrieval          |
| MCP          | Connect AI to tools/data                 |
| AI Agent     | Orchestrate multiple steps               |

A simple memory trick:

```text
LLM       → Think / Understand / Generate

RAG       → Find relevant knowledge

Vector DB → Store/search semantic representations

Indexer   → Prepare knowledge for search

MCP       → Connect AI to tools

ASP.NET   → Execute application logic

SQL       → Store transactional data

Agent     → Orchestrate the workflow
```

# The most important principle

AI should **not replace deterministic insurance business rules**.

For example:

```text
Premium calculation
Policy eligibility
Payment processing
Claim transaction
Authorization
Audit
Compliance
```

should remain controlled by your application/business rules. AI is excellent for:

```text
Understanding
Summarization
Knowledge retrieval
Natural-language interaction
Document analysis
Recommendations
Workflow assistance
```

So the real architecture is:  **Traditional software + AI capabilities**

not:  **AI replacing traditional software.** That is what I mean by an **AI-Enabled ASP.NET Insurance Application**.
