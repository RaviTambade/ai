🌱 **Stateful AI Agents with .NET — From RAG & MCP to Agentic Workflows**

We have been building our Insurance Application step by step. First: **ASP.NET Core + SQL Server** Then: **APIs → LLM → RAG → Tools → MCP → Orchestration** Now we reach a much more interesting question: **What happens when an AI workflow cannot be completed in one straight line?** Because real enterprise problems are rarely:

```text id="r4q9sa"
Prompt
  ↓
LLM
  ↓
Answer
```

A real insurance claim may require:

```text id="4g1z7v"
Customer Question
       ↓
Identify Customer
       ↓
Find Policy
       ↓
Check Coverage
       ↓
Retrieve Claim Rules
       ↓
Check Claim Status
       ↓
    ┌───────────────┐
    │ Is information│
    │ sufficient?   │
    └───────┬───────┘
            │
       No   │   Yes
       ↓    │    ↓
   Ask User │ Generate Answer
       │
       └──→ Continue
```

Now we have: **state + decisions + branching + loops + retries.** This is where **graph-based agent orchestration** becomes powerful.

 

# 🧠 Think in terms of a Graph

Instead of writing one giant agent method, model the workflow as a graph.

```text id="z4q6pn"
                  START
                    ↓
              Understand Intent
                    ↓
              Get Customer
                    ↓
               Get Policy
                    ↓
             Check Coverage
                ↙       ↘
             Valid      Invalid
               ↓           ↓
          Check Claim    Respond
               ↓
        ┌──────┴───────┐
        ↓              ↓
    Information     Missing Data
     Complete           ↓
        ↓          Ask Customer
     Generate           ↓
     Response       Continue Loop
```

- Each box is a **node**.
- Each connection is an **edge**.
- Some edges are conditional.
- Some workflows can loop.

That is the core idea behind graph-based agent orchestration.

# 1️⃣ State — “What do we know so far?”

An agent needs memory of the current workflow. For our insurance application, state might contain:

```text id="x1q3ra"
CustomerId
PolicyId
ClaimId
Intent
PolicyDetails
ClaimDetails
RetrievedDocuments
ToolResults
ValidationErrors
CurrentStep
FinalAnswer
```

Conceptually:

```csharp id="6n7z4f"
public class InsuranceAgentState
{
    public int? CustomerId { get; set; }
    public int? PolicyId { get; set; }
    public int? ClaimId { get; set; }

    public string? Intent { get; set; }

    public PolicyDto? Policy { get; set; }
    public ClaimDto? Claim { get; set; }

    public List<string> RetrievedContext { get; set; }
        = new();

    public string? FinalAnswer { get; set; }
}
```

Now every node operates on a **shared, strongly typed state**. That's an important .NET advantage. We are not passing random dictionaries everywhere. We can model the workflow using familiar C# types.

 

# 2️⃣ Nodes — “One responsibility at a time”

Instead of:

```text id="r9u4p1"
InsuranceAgent()
{
    // 1000 lines
}
```

we create focused nodes.

```text id="w9x5ka"
IdentifyIntent
      ↓
LoadCustomer
      ↓
LoadPolicy
      ↓
CheckCoverage
      ↓
RetrieveKnowledge
      ↓
CheckClaim
      ↓
GenerateResponse
```

Each node does one meaningful job.

For example:

```csharp id="2gq1mk"
async Task CheckCoverage(
    InsuranceAgentState state)
{
    // Call insurance business service
    // Update state
}
```

This is not only AI engineering. It is good **software engineering**.
 

# 3️⃣ Edges — “What happens next?”

A normal workflow is straightforward:

```text id="e4u2jd"
A → B → C → D
```

But enterprise workflows often branch. For example:

```text id="s6u9oa"
                 Check Coverage
                       ↓
                ┌──────┴──────┐
                ↓             ↓
             Covered       Not Covered
                ↓             ↓
          Check Claim       Respond
```

The routing decision becomes part of the graph. Now our AI workflow isn't just a chain. It is a **state machine with intelligence**.

 

# 4️⃣ Loops — “We aren't done yet.”

Imagine the agent discovers: “The claim number is missing.” Instead of failing:

```text id="8f2zq4"
Missing Claim ID
      ↓
     STOP
```

the workflow can:

```text id="q7m5x2"
Missing Claim ID
      ↓
Ask Customer
      ↓
Receive Claim ID
      ↓
Update State
      ↓
Check Claim
```

That's a loop. And loops are exactly where simple prompt chains become difficult to manage.

 

# 5️⃣ Tools — “Use the existing .NET application.”

This is where our previous MCP discussion becomes valuable. Our agent doesn't need to reinvent insurance business logic. We already have:

```text id="z7s5la"
CustomerService
PolicyService
ClaimService
PremiumService
DocumentService
```

Expose the appropriate capabilities through controlled tools. Then:

```text id="6x6y9c"
Agent
  ↓
Tool
  ↓
Existing .NET Service
  ↓
Business Rules
  ↓
SQL Server
```

The AI is not replacing our business application. **It is orchestrating it.** That's a very important distinction.
 
# 6️⃣ RAG — “Find the business knowledge.”

Suppose the customer asks: “Why was my claim rejected?” The agent may need:

```text id="k3y0e1"
Claim Data
     +
Policy Data
     +
Claim Guidelines
     +
Coverage Rules
     ↓
     RAG
     ↓
Relevant Context
```

The graph can have a dedicated retrieval node:

```text id="g1p3tu"
RetrieveInsuranceKnowledge
              ↓
       RetrievedContext
              ↓
        Reason / Decide
```

Now RAG becomes one capability inside a larger workflow.

 

# 7️⃣ Planning — “What should I do next?”

An LLM can help determine the next action. For example:

```text id="m3b7jk"
User:
"Is my hospitalization covered,
and if so, how do I claim it?"
```

The agent might reason that it needs:

```text id="t8x5pw"
1. Customer
2. Active Policy
3. Coverage
4. Relevant Policy Rules
5. Claim Requirements
```

- The graph controls **what actions are allowed**.
- The model helps with **understanding and decision-making**.
- That combination is powerful.

# 🛡️ 8️⃣ Guardrails — “AI should not do anything it wants.”

This is where graph-based architecture has a major advantage. We can explicitly define:

```text id="3r5kqv"
AI Decision
    ↓
Authorization Check
    ↓
Tool Policy
    ↓
Execute Tool
```

For example:

A customer may:

- ✅ View own policy
- ✅ View own claim
- ✅ Check claim status

But should not:

- ❌ View another customer's claim
- ❌ Modify policy without authorization
- ❌ Approve their own claim
- ❌ Access internal underwriting information

The graph gives us explicit places to enforce these boundaries.

 

# 🔄 9️⃣ Retry and Failure Handling

Distributed systems fail.
APIs fail.
Databases fail.
LLMs fail.
Network calls timeout.
A production agent must expect failure.
For example:

```text id="n2v5wr"
Call Claim API
      ↓
   Failure?
    ↙    ↘
  No      Yes
  ↓        ↓
Continue   Retry
           ↓
       Retry Limit?
         ↙    ↘
       No      Yes
       ↓        ↓
     Retry    Escalate
```

This is much safer than allowing an uncontrolled agent loop to continue indefinitely.



# 💾 🔟 Persistence & Checkpointing

Now imagine a claim workflow takes 20 minutes. Or perhaps: **2 days.** The customer uploads a missing document tomorrow. Should we start from the beginning? Not necessarily. We can persist the workflow state.

```text id="y9x3e2"
Agent State
    ↓
Checkpoint
    ↓
Database
```

Later:

```text id="q1p4mz"
Resume Workflow
      ↓
Load Checkpoint
      ↓
Continue from previous state
```

This is extremely valuable for:

→ Long-running workflows
→ Human approval
→ Document verification
→ Asynchronous processing
→ Retry after failure
→ Multi-step claims processing

Now the agent becomes **stateful**.
