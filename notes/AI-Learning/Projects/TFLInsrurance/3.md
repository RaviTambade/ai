# 🤖 What is RAG?

A Large Language Model has general knowledge.

But it doesn't automatically know:

> “What is *our company's* claim rejection policy?”

> “What documents are required for a health insurance claim?”

> “What is the eligibility rule for Policy XYZ?”

> “Why was customer Ravi's claim rejected?”

That knowledge may exist inside:

📄 Policy documents
📄 Claim guidelines
📄 Product brochures
📄 Underwriting rules
📄 Internal manuals
📄 FAQs
🗄️ Database records
🔌 Business APIs

RAG connects the LLM to that information.

# 🔥 The RAG Pipeline

A typical RAG architecture looks like:

```text
Documents / DB / APIs
          ↓
      Ingestion
          ↓
       Chunking
          ↓
      Embeddings
          ↓
     Vector Store
          ↓
       Retrieval
          ↓
   Relevant Context
          ↓
    Prompt + Context
          ↓
         LLM
          ↓
       Response
```

Let's understand each step using our insurance application.

---

# 1️⃣ Data Ingestion

Suppose the insurance company has:

```text
claim_guidelines.pdf
health_policy.pdf
motor_policy.pdf
rejection_rules.pdf
customer_faq.docx
```

Our .NET application reads these sources.

But RAG isn't limited to documents.

We can retrieve information from:

→ SQL Server
→ REST APIs
→ CRM
→ Policy Management System
→ Claims System
→ Knowledge Base

The first engineering challenge is:

> **How do we bring trustworthy business knowledge into the AI pipeline?**

---

# 2️⃣ Chunking

A 100-page insurance document isn't necessarily sent to the LLM as one huge piece.

We divide it into meaningful chunks.

For example:

```text
Claim Guidelines
       ↓
 ┌───────────────┐
 │ Eligibility   │
 ├───────────────┤
 │ Documentation │
 ├───────────────┤
 │ Verification  │
 ├───────────────┤
 │ Rejection     │
 └───────────────┘
```

Good chunking matters.

Too large:

**Retrieval becomes noisy.**

Too small:

**Context loses meaning.**

So chunking is not just a technical preprocessing step.

**It is a knowledge-design problem.**

---

# 3️⃣ Embeddings

Now we convert each chunk into a numerical representation called an **embedding**.

Conceptually:

```text
"Claim requires hospitalization documents"
                 ↓
          Embedding Model
                 ↓
      [0.12, -0.34, 0.78, ...]
```

The goal is to represent the semantic meaning of the text so that related questions can be matched with relevant knowledge.

---

# 4️⃣ Vector Database

Those embeddings can be stored in a vector store.

For example:

→ Qdrant
→ Pinecone
→ SQL Server with vector capabilities
→ Other vector databases

Think:

```text
Insurance Knowledge
        ↓
   Vector Store
        ↓
 ┌──────────────────────┐
 │ Embedding            │
 │ Document             │
 │ Policy               │
 │ Claim Rule           │
 │ Metadata              │
 └──────────────────────┘
```

Metadata becomes very important.

For example:

```text
PolicyType = Health
DocumentType = ClaimGuideline
Version = 2026
Region = India
```

Why?

Because retrieving **similar text isn't enough**.

We also need the **right business context**.

---

# 5️⃣ Retrieval

Now a customer asks:

> **“Why can my claim be rejected?”**

The question itself is converted into an embedding.

The system searches the vector store.

It might retrieve:

```text
Claim Rejection Guidelines
       ↓
Documentation requirements
       ↓
Eligibility conditions
       ↓
Verification rules
```

This is the **R** in RAG:

**Retrieval.**

---

# 6️⃣ Augmentation

We don't simply ask the LLM:

> “Why are insurance claims rejected?”

Instead, we give it relevant business context.

Conceptually:

```text
System Instructions
       +
User Question
       +
Retrieved Insurance Knowledge
       ↓
      LLM
```

Now the model has access to information retrieved from our organization's knowledge base.

---

# 7️⃣ Generation

The LLM produces the final response.

For example:

> “According to the current claim guidelines, the claim may be rejected when required documentation is missing or when the policy conditions are not satisfied.”

The answer is grounded in retrieved business information rather than relying solely on the model's pretrained knowledge.

---

```text

                        ↓

                        ↓
                   .NET API
                        ↓
              ┌─────────┴─────────┐
              ↓                   ↓
          RAG Retrieval       Business APIs
              ↓                   ↓

              │                   │
              └─────────┬─────────┘
                        ↓
                  Context Builder
                        ↓
                       LLM
                        ↓
                    Response
```

Now the AI can combine:

**organizational knowledge**

with

**current transactional data**.

That is where RAG becomes much more powerful.

# 🚨 But here's the mentor warning

RAG does **not** magically make an LLM truthful.

A production RAG system must think about:

→ Data quality
→ Chunking strategy
→ Embedding quality
→ Retrieval accuracy
→ Metadata filtering
→ Access control
→ Prompt design
→ Hallucination
→ Evaluation
→ Observability
→ Data freshness

And in insurance, there is an additional responsibility:

**Authorization.**

A customer should not be able to retrieve another customer's policy or claim information simply because the information exists in the database.

So RAG must respect:

```text
Who is asking?
      ↓
What are they allowed to see?
      ↓
What data can be retrieved?
      ↓
What can the LLM use?
```

**Security is part of RAG architecture.**

**Retrieve authorized customer/policy/claim information**

**Combine the context**
