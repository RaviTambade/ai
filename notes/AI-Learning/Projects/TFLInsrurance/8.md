🌱 **Observability for AI Agents — If You Can't See It, You Can't Improve It**

We have been building our Insurance AI application step by step. We started with: **ASP.NET Core + SQL Server** Then added: **LLM → RAG → Tools → MCP → Orchestration → Stateful Agents** Now comes a problem every production AI engineer eventually discovers:  **The agent works… until it doesn't.**
A customer asks: “Why is my claim still pending?” The AI responds: “Your claim is approved.” 😨 Now the engineering team has questions:

**What happened?**
- Did RAG retrieve the wrong document?
- Did the agent call the wrong tool?
- Did the Claims API return incorrect data?
- Did the LLM misunderstand the context?
- Did the prompt contain the wrong information?
- Did a retry execute twice?
- Did the model consume 10× more tokens than expected?

Without observability… **we are guessing.**

# 🧠 Think in terms of a Trace

Suppose the customer asks:  **“Why was claim CLM1024 rejected?”** Our trace might look like:

```text id="e6t3nr"
Trace: ClaimExplanation
│
├── Intent Classification
│
├── Get Customer
│
├── Get Policy
│
├── Get Claim
│
├── RAG Retrieval
│   ├── Vector Search
│   ├── Document #142
│   └── Document #318
│
├── Generate Explanation
│
└── Final Response
```

Now we can see the **entire journey**. This is the difference between: **“The AI gave a wrong answer.”**
and **“The AI retrieved the wrong policy version before generating the answer.”** The second statement is actionable.

# 1️⃣ Instrumentation

The first step is to instrument the application. Our ASP.NET Core pipeline might look like:

```text id="v8c2jk"

     ↓

     ↓

     ↓

     ↓
Tools / RAG / LLM
     ↓

     ↓
```

We want trace points around important operations:

```text id="5j3wz8"

Start RAG
Start Tool
Call Insurance API
Call LLM
Parse Response
End Agent
```

The goal isn't to log everything blindly. The goal is: **Capture the information required to understand system behavior.**

# 🚨 But here's the enterprise warning

**Don't blindly log everything.** Our insurance application contains sensitive information. Potentially:

- → Customer details
- → Policy information
- → Claims
- → Medical documents
- → Personal data
- → Authentication information

Therefore: **Observability must respect privacy and security.** We may need:

- → Redaction
- → Masking
- → Access control
- → Data retention policies
- → PII filtering
- → Secure telemetry storage

The rule is: **Debug the AI without creating a second security problem.**

# 6️⃣ Latency Analysis

Suppose our customer waits **8 seconds**. Where did those 8 seconds go? Observability might show:

```text id="d3x6qk"
Intent Detection       0.4 sec
Policy API             0.2 sec
Claim API              0.8 sec
Vector Search          0.3 sec
LLM Call #1            2.1 sec
Tool Call              1.4 sec
LLM Call #2            2.6 sec
--------------------------------
Total                  7.8 sec
```

Now we know where to optimize.

Maybe:

- → Cache policy information
- → Reduce unnecessary LLM calls
- → Parallelize independent operations
- → Improve retrieval
- → Choose a faster model
- → Reduce prompt size

This is where **observability becomes performance engineering**.

The model may have generated a perfectly reasonable answer from **bad context**. This leads to a powerful AI engineering principle: **Bad retrieval can produce a confident wrong answer.** So RAG needs observability too.

# 8️⃣ Evaluation

Production AI cannot be tested only with:

```text id="p3q8zv"

```

The API can return HTTP 200… and still give a terrible answer. We need to evaluate:

- → Relevance
- → Groundedness
- → Correctness
- → Tool selection
- → Retrieval quality
- → Structured output validity
- → Safety
- → Regression

For example:

```text id="z8f4qs"
Question
   ↓
Expected Answer / Criteria
   ↓
AI Response
   ↓
Evaluator
   ↓
Score
```

Now we can compare:

```text id="z6n1tx"

Model B → 91%

Prompt V1 → 84%
Prompt V2 → 93%

RAG V1 → 78%
RAG V2 → 90%
```

This turns AI development into an **engineering discipline**.

# 🎯 Mentor takeaway

Traditional software engineering taught us: **If you can't reproduce the bug, it's difficult to fix it.**
AI engineering adds another challenge: **If you can't see what the model saw and what the agent did, it's difficult to understand the failure.** So don't build an AI agent and stop at:**“It works.”** Ask:

- **Can I trace it?**
- **Can I measure it?**
- **Can I evaluate it?**
- **Can I reproduce failures?**
- **Can I control cost?**
- **Can I protect customer data?**
- **Can I improve it from production feedback?**

That's the difference between:**AI Demo** and **Production AI Engineering.**

🌱 **Transflower Mentor**
